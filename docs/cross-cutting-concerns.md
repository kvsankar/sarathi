# Extra Checks By Risk

Use this table when a risk needs work in more than one delivery stage. Choose the review
level and relevant extra checks using [assurance-profiles.md](assurance-profiles.md). Stage
instructions reference the relevant rows instead of repeating the whole table.

| Risk | Requirements say | Design decides | Plan assigns | Code and review prove |
| --- | --- | --- | --- | --- |
| Logs and monitoring | Who needs diagnostic information, privacy limits, and what need not be monitored. | Events, metrics, traces, correlation, redaction, dashboards, alerts, and provider. | Which PR adds each signal or alert, commands and environments used to check it, thresholds, dashboards, and alerts. | Signals are stable and useful, correlation works, private data is removed, and export settings work. |
| Errors | What users, APIs, and operators should see when work fails. | Recovery, retries, fallback behavior, reduced-service behavior, and safe messages. | Which PR implements and tests each failure path. | Realistic failures produce useful messages and logs do not leak private data. |
| External systems and fakes | Exact contracts and acceptance checks against the real interface. | How contract changes are detected, how imports or types remain compatible, and how the real interface will be tested. | Unit, contract, integration, and real-system checks, including a focused real-interface check. | Treat project-written fakes as remaining risk, check real behavior or type compatibility, and do not test an important external interface only through those fakes unless the remaining risk is explicitly accepted. |
| Test environments | Which environments matter and which do not. | Developer, integration, staging, canary, and synthetic environments that are needed. | Setup, data, secrets, reset, smoke tests, rollback, and owner. | Planned environment checks run. Live production checks require explicit approval. |
| UI approval | `UI Mock Preference: Required | Optional | Not needed | Deferred` and any approved prototype. | Whether to reuse the prototype or create only the needed screens and states. | PRs and visual or accessibility checks tied to the approved UI. | Production UI work stops if required UI intent is missing or unapproved. |
| Build and deployment | Required build, release, and deployment behavior. | Outputs, packages, environments, deployment, and rollback. | Files and checks for build, dry run, smoke test, and rollback. | Outputs build and deployment checks pass. Live deployment requires explicit approval. |
| User and developer docs | Audience, needs, acceptance criteria, and non-goals. | Source files, generated docs, publishing, and validation. | Which PR updates each document and runs its checks. | Documentation is updated and checked with the implementation. |
| Security | Protected behavior and credible ways it could be abused. | Trust, enforcement owner, data and secret handling, mitigations, and tests. | Who implements and tests each mitigation, remaining risk, and reasons to stop. | For each changed trust boundary, identify credible abuse cases, assign and implement mitigations, test them through the real enforcement point, and state remaining risk. |
| Reliability | Required retry, fallback, reduced-service, and recovery behavior. | Limits, state changes, recovery owner, monitoring, and tests. | Failure tests, environment, owner, and reasons to stop. | Force each important failure path and verify recovery, side effects, and monitoring. |
| Other risks | Relevant performance, privacy, accessibility, cost, or compatibility needs. | The chosen response, risks, and tests. | Review and test work, or an explicit reason to defer it. | Run the planned checks and revise earlier documents when a new material risk appears. |
| Approvals | Which decisions need a person or an allowed automatic policy. | Where approval is required and which document owns it. | What work depends on each approval. | The local approval matches the current file; reports state its source and limits. |
| Requirement links | Requirement and acceptance IDs. | Component and test IDs. | Which PR owns each requirement and test. | Implemented tests have clear pass/fail checks. Use a full inventory only when needed. |
| Tests across scopes | Product, feature, and change `AT-` and `JT-` items. | Executable `TEST-` items for local, feature, and product behavior. | Earlier tests assigned to child work or PRs, including integration work that spans children. | Each change runs its assigned parent and local tests. A link alone does not prove the test ran. |
